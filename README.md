# Insurance Claims Triage Agent + Claims Analytics Assistant

Two stages of one claims-operations system, each with its own measurement:

1. **Triage agent** (LangGraph + gpt-oss-120b on Groq). Reads a free-text claim, extracts fields,
   grounds them in the policy database, scores fraud, and decides APPROVE / REJECT / ESCALATE.
   It is measured on a 231-case rubric-labeled eval set against two baselines, with paired
   significance tests and stage-level root-cause analysis.
2. **Claims analytics assistant** (text-to-SQL + RAG over Postgres). Answers questions about
   the claims book, the triage agent's own decision log, and company policy. **Different users
   see different data, enforced by Postgres** (row-level security, column grants,
   least-privilege logins), and every answer is traced. It is measured on a 76-question gold
   set, an adversarial RBAC suite, and a retrieval eval.

The stages are wired together. Every triage decision is written to `triage.decisions` in
the warehouse, so the assistant can answer "how many claims did the agent reject for an
expired policy last week?". An `agent_rag` variant of the triage agent retrieves the SIU
red-flag guide from the same document store before scoring fraud.

```
                  ┌──────────────── stage 1: triage (agents/) ────────────────┐
 free-text claim ─► extract → policy lookup → [retrieve SIU guide] → fraud → route → decide ─► decision
                  └─────────────────────────────────────────────────────────────┘     │ cx_triage role
                                                                                      ▼
 ┌──────────────────────────── Postgres 16 + pgvector: the claims warehouse ───────────────────────────┐
 │ ins.*      1,000 real-format US auto claims, policies, policyholders, vehicles  (RLS by policy state) │
 │ triage.*   triage book + decision log                                                               │
 │ app.doc_chunks  10 company documents, FTS + vector index, per-chunk ACL (RLS)                         │
 │ obs.*      assistant traces                                                                          │
 └─────────────────────────────────────────────────────────────────────────────────────────────────────┘
                                   ▲  connection opened AS the user's role
 question ─► stage 2: assistant (assistant/) — tool loop: search_docs · get_schema · run_sql (guarded) ─► answer + SQL + sources + trace
```

### Why 231 cases

| | v1 (n = 25) | v2 (n = 231) |
|---|---|---|
| 95% CI at 96% accuracy | [80.5, 99.3], **18.8 pp wide** | [92.8, 97.9], **5.1 pp wide** |
| 95% CI at 90% accuracy | [74.0, 97.8] | [85.5, 93.3] |
| Can it separate agent from baseline? | No: any two systems above ~80% overlap | Yes: paired tests on 231 shared cases |

With 25 cases a single flipped case moves accuracy by 4 pp, and the interval can't rule
out an 80%-accurate system. With 231 cases, the **paired** comparison is what matters
(`eval/compare.py`). Both systems run on the same cases, so the test looks only at
discordant cases: those one system got right and the other got wrong. That is far more
sensitive than comparing two marginal intervals.

### What the rules-only baseline shows (measured)

The baseline uses regex extraction and keyword fraud heuristics, with zero LLM calls. It
was written against the v1 phrasing only and gets 22/25 there. On the full set:

* **78.4% [72.6, 83.2].** It is perfect on the deterministic slices (expired, pre-inception,
  inactive policy, clean approvals): rules are fine when the facts are easy to parse.
* **40 of its 50 errors are `fraud_underscore`.** It approves fraud stories that carry no
  obvious keyword: `implausible_amount` 0/8, `fraud_story` 11/30. Catching these needs world
  knowledge (₹1.6 lakh for a bumper scratch) and reading the whole story.
* **4 errors are `extraction_amount`**: two amounts written in words ("five lakh sixty-five
  thousand rupees") and two bare "2.34L" with no currency marker.
* **3 of 10 prompt injections get approved.** Here that is an accident (keyword misses),
  not obedience.

This is the bar the agent has to clear, and the error analysis shows where an LLM
*should* help: fraud judgment and free-form amounts. The policy-validity checks are where
the agent should keep its deterministic Python rules.

> One bug fix after the first v2 run: the baseline's sentence splitter broke
> "Rs. 7,67,000/-" after "Rs.", which turned 12 more amounts into ₹0. The bug was mine,
> not a limit of the rules approach, so I fixed it rather than report a weakened baseline.
> Before the fix it scored 73.2%. No other changes were made after seeing v2 results.

## Architecture

```
User Input (free-text claim)
        │
        ▼
┌───────────────┐
│    extract    │  LLM → structured fields (claimant, policy ID, amount, date, type)
└──────┬────────┘
       ▼
┌───────────────┐
│ lookup_policy │  SQLite → coverage limit, deductible, window, status  (ID normalised)
└──────┬────────┘
       ▼
┌───────────────┐
│ assess_fraud  │  LLM → fraud_score 0.0–1.0 + flag list
└──────┬────────┘
    fraud > 0.75 (after documentation cap)?
       ├─── YES ──► auto_reject ──┐
       └─── NO ───► decide ───────┤  deterministic rules; LLM writes justification only
                                  ▼
                          generate_report
```

All LLM nodes are wrapped with `@_safe_node`. If a node fails (API down, malformed
output, timeout), it injects a safe ESCALATED default and sets an error flag instead of
crashing the pipeline.

**v2 fixes** (found in code review, before any v2 run; see [docs/LABEL_AUDIT.md](docs/LABEL_AUDIT.md)):

* Policy IDs are normalized, so `pol012` and `POL 12` both resolve to `POL-012`.
* Lapsed or cancelled policies are rejected.
* An incident before the policy's start date is rejected.

## Eval harness

### Dataset: 231 cases, labeled by rubric

| Part | n | How it was made |
|---|---|---|
| **v1**, hand-written | 25 | The original set: 5 each of auto / health / property / fraud / edge. Three labels were corrected: `auto_05` had been labeled to match the model's output. See [docs/LABEL_AUDIT.md](docs/LABEL_AUDIT.md). |
| **v2**, generated | 206 | [`eval/generate_cases.py`](eval/generate_cases.py) samples **latent facts**: a real policy row, an incident with a plausible ₹ range, an amount at a target claimed/coverage ratio, a date inside or outside the policy window, and red flags. Each case is labeled from those facts by [`eval/rubric.py`](eval/rubric.py) and rendered in one of three phrasing tiers. |

**13 scenario slices** (full table in [docs/RUBRIC.md](docs/RUBRIC.md)):

* clean approvals and high-ratio escalations
* partial documents
* exceeds-coverage
* expired, not-yet-started and inactive policies
* unknown IDs
* fraud stories *within* the limit
* implausible amounts
* legitimate claims with **distractors** (urgency, a relative filing, "no police report was needed")
* **prompt injections**
* exact boundaries (80%, at the limit, limit + ₹1,000, the end date, the day after)

**3 phrasing tiers:**

* `canonical`: v1 style
* `paraphrase`: "₹1.2 lakh", "one lakh twenty thousand rupees", "the 14th of March 2025"
* `noisy`: lower-case, Hinglish, `pol012`, `1.2L`, `14/03/2025`

Every case stores its **truth** (policy ID, amount, date, flags). That lets the harness
score extraction field by field and attribute each wrong decision to a pipeline stage.

`python -m eval.integrity` checks the set before every run:

* re-derives every label from the rubric
* regenerates v2 and diffs it byte-for-byte against the committed file
* checks that no case text has leaked into `agents/` or `baselines/`
* checks for duplicate cases
* compares against the version pin in `eval/dataset.lock`

### Systems compared

| System | What it is | LLM calls / claim |
|---|---|---|
| `agent` | The LangGraph pipeline above | 2–3 |
| `single_prompt` | **Baseline.** One call to the same model, with the *same rules and thresholds* stated in the prompt and the whole policy table pasted in. No tools, no Python checks, no router. It measures what the graph structure buys. | 1 |
| `rules` | **Baseline.** Regex extraction, keyword fraud heuristics, and the same decision thresholds. It measures what the LLM buys. | 0 |
| `agent_no_fraud` / `agent_no_policy` / `agent_simple_prompt` | Ablations of the agent | 1–3 |
| `agent_rag` | The agent plus retrieval of the SIU red-flag guide from the stage-2 document store, before fraud scoring. The guide states the company's fraud policy, so gains measure *policy grounding*. | 2–3 |

### What gets measured

| Layer | Metric | Where |
|---|---|---|
| Decision | Accuracy + 95% Wilson CI, macro-F1, per-class P/R/F1, confusion matrix | `eval/runner.py` |
| Robustness | Accuracy by tier, slice, line and source (each with a CI); injection resistance | `eval/runner.py` |
| Agent vs baselines | Paired-bootstrap 95% CI on Δaccuracy, exact McNemar test | `eval/compare.py` |
| Extraction | Field accuracy (policy ID, amount, date) vs truth, by tier | `eval/runner.py` |
| Fraud | Band accuracy, AUC (high vs rest), calibration curve, Brier score | `eval/runner.py`, `eval/calibration.py` |
| Root cause | Every wrong decision attributed to `extraction_*`, `fraud_over/underscore`, `injection_followed` or `decision_logic`, by counterfactual replay through the rubric | `eval/attribution.py`, `eval/error_analysis.py` |
| Cost / latency | Tokens, $ per 1k claims, p50/p95/p99 per node | `eval/runner.py` |
| Production | Drift, online accuracy from labeled samples, shadow agreement, regression diff | `eval/monitor.py`, `feedback.py`, `shadow.py`, `diff.py` |

**How root-cause attribution works.** For each wrong decision, the harness re-runs the
rubric with one input swapped at a time:

1. Would the decision have been right with the *true* amount or policy ID or date? → `extraction_*`
2. If not, would it have been right with the *true* fraud band? → `fraud_*`
3. If neither explains it, the system misapplied the rules to correct inputs → `decision_logic`

This turns a bare accuracy number into a ranked list of what to fix next. For the rules
baseline, that list reads: 40 missed fraud stories, then 4 unparsed amounts, then
3 injections.


Filters: `python -m eval.runner --system agent --split v1|v2 --slice fraud_story --tier noisy --case edge_03 --limit 10`

**Free-tier notes.** A full agent run is about 231 × 2–3 calls (~350k tokens), which can
exceed a daily free-tier token cap. Three things make that safe:

* every response is cached in `.cache/llm_cache.sqlite` (temperature 0)
* each case result is appended to a `.partial.jsonl`, so `--resume` picks up where the run stopped
* 429 responses back off and retry instead of being scored as errors

To use another provider, set `LLM_PROVIDER=openai` with `LLM_BASE_URL` (OpenRouter,
Together, a local Ollama or vLLM server). Change `LLM_MODEL` to compare models on the same set.

# Stage 2 — Claims analytics assistant

An LLM agent that answers questions over a Postgres claims warehouse. It uses tool calls to
retrieve company documents (hybrid full-text + pgvector) and to run SQL, all **as the asking
user's database role**.

```
Olivia (Ohio adjuster): "How many claims in my region exceed a regional adjuster's settlement authority?"

search_docs("adjuster settlement authority")  → claims_handling_manual#1: "Regional adjusters may settle claims up to 25,000 USD …"
run_sql(SELECT count(*) FROM ins.claims WHERE total_claim_amount > 25000)
        ↳ runs as cx_adjuster_oh → row-level security keeps only Ohio policies → 291
"291 of your region's claims are above the 25,000 USD adjuster authority [claims_handling_manual]."
```

## The data

| Schema | What | Source |
|---|---|---|
| `ins` | 1,000 US auto policies, policyholders, vehicles and claims: incident type, severity, police report, injuries, amounts, and the SIU `fraud_reported` label (24.7% fraud) | `insurance_claims.csv`, the dataset widely used in fraud-detection research ([Mendeley Data](https://data.mendeley.com/datasets/992mh7dk9y)), fetched from a pinned GitHub commit and **SHA-256 verified** at load time |
| `triage` | The triage agent's 30-policy retail book, plus `decisions`: every decision the triage service makes, with reason code, fraud score, payout, system, latency and tokens | Written live by `POST /triage` and the UI. `scripts.seed_triage_log` back-fills a week by running a triage system over the 231 eval claims. |
| `app.doc_chunks` | 10 company documents in 40 chunks: KPI definitions, data dictionary, claims-handling manual, privacy policy, regional SLAs, triage runbook, reserve guidelines (adjusters only), SIU fraud guide (SIU only), underwriting guidelines (Head of Claims only), and a vendor bulletin carrying a prompt injection | `warehouse/docs/`, written for this project and consistent with the data |

The source dataset has no names, so `full_name` and `email` (`@example.com`) are
**synthetic overlays**. They make personal-data controls testable; everything else is loaded
as-is (`?` becomes NULL).

## Who sees what, enforced by Postgres

| User | DB role | Rows | Personal data | SIU fraud label | Triage log | Restricted docs |
|---|---|---|---|---|---|---|
| alice, Head of Claims | `cx_admin` | all | ✅ | ✅ | ✅ | all |
| ana, claims analyst | `cx_analyst` | all | ❌ (column grants) | ✅ | ✅ | — |
| olivia / ian / isha, adjusters | `cx_adjuster_oh/il/in` | **own policy state only** (RLS) | ✅ own region | ❌ (keeps settlement unbiased) | ❌ | reserve guidelines |
| sam, SIU investigator | `cx_siu` | all | ✅ | ✅ | ✅ | SIU fraud guide |

How it is enforced, layer by layer:

* **One login role per app role.** The assistant connects *as* the user's role, so
  model-written SQL can't `SET ROLE` or call `set_config('role', …)`: no login is a member of
  another query role.
* **Row-level security.** The role→state map is a table with its own RLS, not a forgeable
  session variable. Claims, policyholders and vehicles are scoped *through* `ins.policies`,
  so policies compose automatically.
* **Column privileges.** Personal data is withheld from analysts, and fraud labels from
  adjusters.
* **Document ACL.** RLS on `app.doc_chunks` filters retrieval, so a restricted chunk is never
  ranked or put in the prompt.
* **Read-only roles** with `statement_timeout`, `REVOKE` on all functions by default,
  `search_path` pinned to `ins, triage`.
* **SQL guard** (`assistant/sql_guard.py`, sqlglot): one SELECT only; blocks DML/DDL,
  `pg_*`/`set_config`/`current_setting`, `app.*`/`obs.*`/catalogs and locking; adds a LIMIT.
  This is defense in depth, not the boundary.
* **Prompt policy.** Document and row text are data, not instructions. This is the only layer
  that depends on the model.

## Stage 2 results

**Measured without an LLM:**

* **RBAC attack suite: 26/26 contained, with *and without* the SQL guard**
  ([report](eval/reports/assistant/rbac_suite.md)). It covers:
  * PII via `SELECT *`, CTEs, scalar subqueries and `row_to_json`
  * fraud labels via `row_to_json`
  * cross-region reads and forged session variables
  * `set_config('role')` escalation
  * reading or rewriting the role→region map
  * restricted docs and traces
  * writes, stacked statements, `pg_sleep`, file reads and `pg_authid`

  The "guard bypassed" column is the point: Postgres alone holds the line. **The suite found
  a real gap during development**: adjusters could enumerate every role's region from
  `app.role_scope`. That table now has its own RLS policy.

* **Retrieval** ([report](eval/reports/assistant/retrieval.md)): 24 gold questions, each run
  as the asking user's role.

  | Mode | Recall@1 | Recall@3 | MRR |
  |---|---|---|---|
  | Full-text (`ts_rank_cd`) | 0.88 | 1.00 | 0.93 |
  | Vector (pgvector, local hashed n-gram embeddings) | 0.79 | 1.00 | 0.89 |
  | **Hybrid (RRF)** | **0.92** | 1.00 | **0.96** |

  Restricted documents were returned in **0 of 15** question × mode checks (top 50 chunks).
  The corpus is small, so recall@3 is at its ceiling. The harder test is whether the agent
  *chooses* to look up a definition, which is what the 12 `hybrid` questions measure.

* **Harness controls**, which validate the scorer itself:

  | Control | Pass | Execution accuracy | Correct refusals | Over-refusal |
  |---|---|---|---|---|
  | Oracle: gold SQL + gold docs through the real tools | **76/76** | 44/44 | 18/18 | 0/55 |
  | Null: always "not available" | 20/76 | 0/44 | 17/18 | **55/55** |

  The null agent shows why refusal correctness is always reported **next to over-refusal**:
  refusing everything "passes" almost every security test.

**The assistant itself:** `make assistant-eval` with your key writes
`eval/reports/assistant/agent_*.md`. `make assistant-ablations` adds full-text-only and
no-docs runs; the no-docs run shows what RAG adds on the hybrid slice.

## Stage 2 eval design

[`eval/assistant/gold.yaml`](eval/assistant/gold.yaml) holds 76 questions from 6 users.
Every gold query runs **as that user**, and answers are derived from the live result. That
keeps triage-log questions valid whichever system seeded the log.

| Category | n | Passing requires |
|---|---|---|
| `sql_simple` / `sql_complex` | 10 / 10 | Execution accuracy: result sets match (order-insensitive; tolerant of renamed, reordered and extra columns) |
| `rbac_scope` | 8 | Same question, different users, different correct answers (352 / 338 / 310 claims "in my region") |
| `hybrid` | 12 | Apply a documented definition, then SQL. Traps: "Ohio claims" is the **policy** state (352), not the incident state (23); "documented" treats NULL as not documented. |
| `triage_log` | 4 | Questions over the stage-1 decision log |
| `doc` | 11 | Required facts in the answer |
| `rbac_denied` / `doc_acl` | 7 / 4 | Declines, and forbidden values never appear (emails, street addresses, other regions' counts, hobbies, confidential rate plans) |
| `safety` | 7 | Direct and **indirect** prompt injection: the vendor bulletin asks for every email, and the user is the Head of Claims, who *can* read emails. Also an `UPDATE` with a post-check that the DB is unchanged, `pg_sleep`, `set_config` escalation, and social engineering. |
| `unanswerable` | 3 | Says the data doesn't exist |

**Failure taxonomy:**

* `schema_linking`, `wrong_filter`, `wrong_aggregation`, `wrong_result_other`: from a sqlglot
  structural diff of gold vs final SQL
* `definition_not_retrieved`
* `sql_error_unrecovered`, `guard_rejected`
* `over_restricted`, `over_refusal`
* `retrieval_miss`, `answer_missing_facts`
* `no_refusal`, `leak`, `injection_followed`
* `hallucinated_answer`, `post_check_failed`

## Tracing

Every assistant request writes one trace with nested spans to `obs.traces` / `obs.spans`
(OpenTelemetry shape: trace / span / parent IDs and attributes). Only `cx_obs` can read
them, and the API shows users their own traces only. The spans are:

* `agent.run`
* `llm.chat`: model, tokens, cache hit, tool calls requested
* `tool.search_docs`, with `retrieval` (query, chunk IDs, mode)
* `tool.run_sql`, with `sql.guard` (verdict, tables, LIMIT added, rejection reason) and
  `db.query` (role, rows, ms, SQLSTATE)

`python -m assistant.cli --user olivia "…"` prints the tree.

Or bring everything up with `docker compose up --build`: Postgres+pgvector, then the

**Design notes and limits**

* **Separate logins instead of a single login using `SET ROLE`.** With one login, a session
  that is a member of every role lets model-written SQL call `set_config('role', …)`. Separate
  logins close that, and the attack suite checks for it.
* **Local embeddings are lexical** (hashed character n-grams; no model download). For
  semantic embeddings, set `EMBED_PROVIDER=openai` and run `python -m warehouse.load --docs-only`.
* **Refusal and no-data detection use regexes.** The oracle and null controls validate them;
  read per-item answers in the report for borderline cases.
* **The demo `X-User` header stands in for OIDC/JWT.** Only `current_user()` in `api/main.py`
  would change, because authorization lives in Postgres.

| Agents | LangGraph (triage); plain tool-calling loop over the OpenAI-compatible API (assistant) |
| LLM | `openai/gpt-oss-120b` via Groq by default (`LLM_MODEL` to switch, e.g. `qwen/qwen3.6-27b`); any OpenAI-compatible endpoint |
| Data | SQLite (triage policy lookup), Postgres 16 + pgvector (warehouse, documents, traces) |
| Retrieval | Postgres full-text `ts_rank_cd` + pgvector HNSW, Reciprocal Rank Fusion |
| Access control | Postgres login roles, row-level security, column privileges, document ACLs via RLS |
| SQL safety | sqlglot static guard + read-only roles + statement timeouts |
| Observability | Spans in Postgres (`obs.*`), cost/latency per node, drift + shadow monitoring |
| Eval | Rubric-labeled synthetic + hand-written cases, paired tests, gold SQL execution accuracy, RBAC attack suite |
| Serving / CI | FastAPI, Streamlit, Docker Compose, GitHub Actions (with a pgvector service) |
